# Xencode Context Architecture

**Status:** Design spec (v0.1) — not implemented
**Date:** 2026-09-09
**Scope:** Local-first context engine for small models (4B–7B, limited VRAM). Turns a limited context window into an apparently much larger working memory by separating *context* from *memory*.

---

## 0. Golden rule

**Context is not memory.**

- Context = what the model sees this request (bounded by `ctx_size`).
- Memory = everything we know about the project and task, stored as files on disk, revealed on demand.

Never give the model the repository. Give it a **map**, then give it **pieces of the repository when needed**.

---

## 1. Layered memory model

| Layer             | Purpose                      | Lifetime        | Where stored                                  |
| ----------------- | ---------------------------- | --------------- | --------------------------------------------- |
| `AGENTS.md`       | Agent behavior rules         | Permanent       | repo root (user-owned)                        |
| `anchor.md`       | Project map / orientation    | Long-term       | `.xencode/anchor.md`                          |
| `index/`          | Retrieval index (files/symbols/deps) | Long-term | `.xencode/index/`                     |
| `summaries/`      | Per-file knowledge           | Long-term       | `.xencode/summaries/`                         |
| `state.md`        | Current task state           | Session/task    | `.xencode/state.md`                           |
| recent messages   | Conversation                 | Short-term      | in-memory (existing `ConversationMemory`)     |
| KV cache          | Inference acceleration       | Ephemeral       | llama.cpp server                              |
| raw tool output   | Recoverable evidence         | External        | `.xencode/cache/cmd/`                         |

`AGENTS.md` and `anchor.md` have different jobs and are never merged or overwritten interchangeably:

- **`AGENTS.md`** — *how the agent should behave*: coding rules, architecture rules, testing rules, "Rust is source of truth" style directives. Written by humans. `/init` may **append a generated block** but must never rewrite existing rules.
- **`anchor.md`** — *what the project currently is*: architecture, modules, critical files, dependencies, current state, known problems. Generated by `/init`, incrementally refreshed on git changes.

## 2. `.xencode/` directory layout

Created by `/init` in the project root (gitignored by default unless the user opts to commit `anchor.md`).

```text
.xencode/
├── anchor.md                  # the project map (1–2k tokens)
├── state.md                   # current task state (session/task lifetime)
├── index/
│   ├── files.json             # file inventory + LOC + language
│   ├── symbols.json           # extracted symbols per file
│   ├── deps.json              # 1-hop dependency edges (imports)
│   └── manifest.json          # git HEAD + file mtimes → invalidation snapshot
├── summaries/
│   └── <relpath>.md           # one summary per source file (dirs flattened to +)
└── cache/
    ├── cmd/<hash>.txt         # raw command/tool output (recoverable evidence)
    ├── metrics.jsonl          # per-request metrics (append-only)
    └── transcript/<ts>.json   # pre-compaction conversation dumps
```

Rules:
- Paths inside `.xencode/` always use `/` separators.
- Root `.xencode/` should be gitignored (auto-append if absent) unless user opts in — everything except `anchor.md` is regenerable.
- Binary content and secrets are never indexed (see §15).

## 3. `anchor.md` schema (target ≤ 2k tokens, ideal ~1–1.5k)

Template is fixed. Every section is optional but the headers are stable so the model can parse it and `/init` can diff against it.

```markdown
# Project Anchor

## Identity
name: %name
purpose: %one-line
language: %primary + secondary list
framework: %if any

## Architecture
%2–4 line data-flow, e.g. "CLI → Core → Model Router → Providers"

## Modules
| path | purpose | size |
|---|---|---|
| core/ | inference + orchestration | LOC |

## Critical Files
| path | why |
|---|---|
| src/main.rs | CLI entry |

## Dependencies
| name | version | where used |
|---|---|---|

## Contracts
- %one bullet per non-obvious invariant/contract, max 6

## Build & Test
- build: `cargo build`
- test: `cargo test`
- lint: (if present)

## Current State
%generated from git: branch, dirty-file count, HEAD note; 1–3 lines

## Known Problems
- %from summaries with a strong "risk" signal or TODOs
```

Per-section token guidance (approximate, see §10 estimator):
- Identity ~80 · Architecture ~100 · Modules ~150 · Critical Files ~120 · Dependencies ~150 · Contracts ~120 · Build/Test ~60 · Current State ~80 · Known Problems ~80 → ~940 baseline, headroom for modules of larger repos.

**Why a fixed template:** the model needs to locate sections by header; retriever and budgeter can slice by header; diffing regeneration is trivial.

## 4. `/init` pipeline (multi-pass indexing job)

Most passes are deterministic and free. A local 4B/8k model never sees more than one (chunked) file at a time.

### Pass 1 — structural scan (no LLM)
Rust walks the tree:
- files, dirs, extensions, LOC (non-blank, non-comment best effort), sizes
- language detection by extension (allow-list of source extensions; everything else listed as `misc`)
- git branch + `git status --porcelain` counts + git HEAD (see §8)
- dependency manifest parse (best effort): `Cargo.toml`, `package.json`, `pyproject.toml`, `requirements.txt`, `go.mod`
- detect "important" files: `README.md`, `AGENTS.md`, `Dockerfile`, `docker-compose.yml`, CI configs
- skip: `.gitignore`d paths (use `git ls-files` when in a repo; fallback = our exclusion list), `.git`, `node_modules`, `target`, `__pycache__`, `.venv`, `.xencode` itself, binaries, secrets (§15)

Output: `index/files.json`, `index/manifest.json`.

### Pass 2 — deterministic extraction (no LLM, Rust-first)
Lexical/structural extraction, **no feeding source to the model**:

```text
auth.rs
structs: User, Session
functions: authenticate, refresh_token
imports: jsonwebtoken, sqlx
exports: authenticate, refresh_token
LOC: 481
```

- Implement a lightweight **regex/tokenizer extractor** for Rust first; any file whose language has no extractor gets `structural: {}` and falls through to Pass 3 with the raw head of the file.
- `imports` from top-level `use` statements → these produce **1-hop dependency edges** in `deps.json` (map module path → file).
- Tree‑sitter / AST is a later upgrade — do not block on it.

Output: `index/symbols.json`, `index/deps.json`.

### Pass 3 — per-file LLM summaries
For each source file, send the model a compact prompt:

```text
FILE: src/auth.rs

STRUCTURAL DATA:
481 lines, 12 functions, 2 structs, 8 imports

CODE:
[first relevant chunk]
```

> Summarize this file for another coding agent. Preserve responsibilities, public interfaces, dependencies, important invariants, side effects, integration points. Do not explain obvious implementation details.

Output, written to `summaries/src-auth.rs.md`:

```markdown
### src/auth.rs
Purpose: …
Responsibilities: …
Dependencies: database.rs, jwt.rs
Important: refresh_token() requires an existing Session
Public API: authenticate(), refresh_token()
```

### Pass 4 — hierarchical (map→reduce) summarization for huge files
Never feed a 100k-token file to an 8k-context model.

```text
giant_file.rs → chunk1..chunkN (≤ 3k tokens each, 100-token overlap)
                 → summary1..summaryN  (intermediate summaries
                    written to disk, NOT kept in context)
                 → final summary → summaries/giant_file.rs.md
```

- Chunked summaries do not enter the conversation context. Only the final one-line-per-chunk note is stored, with the final synthesis in the summary file.
- Files that exceed a profile-specific "direct read cap" are always handled this way.

### Pass 5 — anchor synthesis (the only "ask-the-model-about-the-whole-repo" step)
A dedicated pass over the accumulated summaries (not the source), in one call:

> You are building an orientation map for a new coding agent. Given the file summaries below, produce `anchor.md` following this exact schema: …

- This is why summaries must be high quality: the anchor is the *summary of summaries*.
- If `anchor.md` exists, `current state`/`known problems` are diffed — the model only regenerates sections flagged by Pass 1/§8 as changed when possible.

**Anchor is NOT regenerated on every chat.** Lifecycle: `/init` full build → git-delta refresh (§8) → occasionally full rebuild on structural change.

## 5. Index formats

### `files.json`
```json
[
  {"path": "src/auth.rs", "language": "rust", "size": 18420, "loc": 481,
   "ext": "rs", "important": false, "ignored": false}
]
```

### `symbols.json`
```json
{"src/auth.rs": {"structs": ["User", "Session"], "functions": ["authenticate", "refresh_token"],
  "imports": ["jsonwebtoken", "sqlx"], "exports": ["authenticate", "refresh_token"]}}
```

### `deps.json`
```json
[{"from": "src/auth.rs", "to": "src/database.rs", "via": "use crate::database"}]
```

### `manifest.json` (invalidation snapshot)
```json
{"git_head": "abc1234", "mtime_map": {"src/auth.rs": 1736400000}, "indexed_at": 1736400000}
```

## 8. Incremental invalidation (git-driven)

- Store `git_head` + file `mtime_map` in `manifest.json` at end of `/init`.
- On session start and on `/init` re-run:
  - If `git_head` changed → `git diff --name-only <old> <new>` → re-summarize **only** changed/added files; delete summaries for removed files.
  - If no git repo → mtime comparison against `mtime_map`.
  - Anchor: only regenerate when structure changed (directories/important files added or removed) or when ≥ N% of files changed (N default 20%) — otherwise update only `Current State`/`Known Problems` with a cheap edit.
- No git changes → `/init` is a no-op that just confirms freshness.

## 9. Retrieval (cheap first, "AI" later)

Initial retriever is deterministic scoring. No embeddings in v1.

Score candidates for the user's latest prompt (`query`) against every indexed file:

| Signal                        | Weight |
| ----------------------------- | ------ |
| filename exact match          | +10    |
| filename substring            | +6     |
| path segment match            | +5     |
| symbol hit (function/struct/var) | +8 (per unique hit, capped +16) |
| git-changed file              | +4     |
| dependency 1-hop from a seed  | +3 (≤3 hops expanded)           |

- **Seed expansion:** files scoring ≥ +10 become seeds; expand the dependency graph one hop from seeds, each hop adds +3.
- **Minimum threshold:** score < 3 → do not inject.
- **Top-K cap (profile):** LOW 3 · BALANCED 5 · HIGH 8.
- **Per-file content cap (chars):** LOW 8k · BALANCED 16k · HIGH 24k.
- Empty/absent query (e.g., a bare follow-up like "fix it") → seed from git-changed files + most recently touched files.

Example:
```
auth.rs +10, +8(symbol) = 18 → seed
database.rs  +4(git) +3(dep edge from auth) = 7 → inject
session.rs   +3(dep edge) = 3 → inject
jwt.rs       +3(dep edge) = 3 → inject
README.md    +1 → skip
```

Retrieved file bodies are inserted as fenced blocks with the path header exactly:
````markdown
File: src/auth.rs
```rust
<content capped>
```
````

## 10. Context builder + token budgeter

### Priority order (fixed, so the head stays byte-stable for KV reuse)
```
1. SYSTEM        (fixed instruction block, ~80 tokens)     STABLE
2. AGENTS.md     (capped 1200 tokens, head of file)        STABLE
3. anchor.md     (capped 2000 tokens)                      STABLE
------------------stable-prefix boundary-------------------
4. state.md      (current task, capped 800 tokens)         DYNAMIC
5. git summary   (branch + changed-file list, capped 300)  DYNAMIC
6. retrieved files (remaining budget after tiers 1–5)      DYNAMIC
7. recent messages (rolling window, fills to target)       DYNAMIC
```

### Deterministic token estimator (no LLM)
- `est_tokens = ceil(chars / 4)` for prose, `ceil(chars / 3)` for code bodies.
- Used only for budgeting. Real counts come from llama.cpp (`usage`) and are what we display/optimize.

### Budget algorithm per request
1. `target = floor(ctx_size × utilization)` where `utilization` is profile-based (LOW 0.6 · BALANCED 0.75 · HIGH 0.85).
2. Reserve `target`; fill tiers in priority order; tiers 4–6 each consume their cap/estimate but **stop consuming once remaining budget < 200 tokens**.
3. Tier 7 (recent messages) gets whatever remains; most-recent messages win (drop oldest first).
4. If tier 7 gets < 1 message of budget → trigger **soft compaction** (§11) and rebuild, once, before generating.
5. Retrieved files are trimmed from the bottom (lowest score first) to fit.

### Why fixed order matters
Bytes 1→3 are identical across consecutive requests → llama.cpp reuses their KV-computed prefix (see §13). Nothing dynamic may precede the stable prefix.

## 11. Compaction — layered, soft vs hard

### Layer separation during compaction
Never "summarize everything" into one blob:

```
conversation →
  ✓ immutable facts    ✓ current task
  ✓ decisions          ✓ completed work
  ✓ unresolved issues  ✓ recent messages
```

### Soft compaction (trigger: usage ≥ 70%)
- Drop old `tool output` blocks (already compressed in §12); keep the command + result summary.
- Drop the oldest 30% of conversation messages, but preserve any message containing a "decision" marker (`[d]`).
- No LLM call. Deterministic. Updates `state.md` field `completed/working-on` only if the model flagged it.

### Hard compaction (trigger: usage ≥ 90% after soft)
- One model call folds the conversation into the layered summary above (`facts / task / decisions / completed / unresolved / recent = last 6 messages`).
- Raw transcript is dumped to `.xencode/cache/transcript/<ts>.json` before rewrite.
- After rebuild: `anchor + AGENTS + state.md + recent(≤6)`. Continue with continuity.

### What is always preserved
`SYSTEM`, `AGENTS.md`, `anchor.md`, `state.md`, decisions, unresolved issues.

## 12. Tool output compression

Huge hidden context killer. Rule: **conversation never retains raw tool output.**

```text
cargo test → 500 lines → stored as .xencode/cache/cmd/<sha256>.txt
```
Conversation retains only:
```text
COMMAND: cargo test
RESULT: FAILED (3 errors)
FILES: auth.rs, router.rs
DETAIL: <up to 4 lines>   ← model's own one-liner if available
RAW: cmd/<hash>.txt
```
Any future request containing `cmd/<hash>` re-reads the raw file from disk on demand.

## 13. KV-cache strategy

### Policy
- **Stable prefix discipline:** force byte-identical `SYSTEM + AGENTS.md + anchor.md` at the front of every prompt. This is the KV-reuse win. Slot persistence enabled.
- **Do not reorder dynamic tiers** — cache reuse degrades if the permutation of retrieved files changes the shared head. (Retrieved files live below the boundary, so they can't shift the prefix.)
- **Initial `llama_cpp_args` defaults (balanced profile):**
  `--flash-attn --cache-type-k q8_0 --cache-type-v q8_0 --ctx-size 8192 --n-predict 1024 --parallel 1`
  (LOW: `--ctx-size 4096`, KV `q8_0+ q4_0-v`; HIGH: `--ctx-size 16384`, KV `q8_0`.)
- KV quantization is a **profile setting**, not a universal flag (§14).

### Measurement-driven tuning
Capture from llama.cpp usage/timings on every request:
- `prompt_tokens` (total), `prompt_tokens_evaluated` (computed this request) → `cached_tokens = prompt_tokens - prompt_tokens_evaluated`
- `completion_tokens` (already captured today)
- surface in the metrics meter (§16) and log `metrics.jsonl`

If `cached_tokens` is persistently ~0 while the stable prefix is large → something is violating prefix stability; that's a bug, not a tuning issue.

## 14. Hardware profiles

Profiles are settings presets + a default. They ARE tunable manually; never hardcoded in logic — logic reads the profile fields.

| Profile   | VRAM target | ctx   | KV cache        | retrieval K | content cap/file | utilization | compaction |
| --------- | ----------- | ----- | --------------- | ----------- | ---------------- | ----------- | ---------- |
| **LOW**   | <4 GB       | 4096  | K q8_0 / V q4_0 | 3           | 8k chars         | 0.60        | early (60/80) |
| **BALANCED** | 4–8 GB   | 8192  | K/V q8_0        | 5           | 16k chars        | 0.75        | adaptive (70/90) |
| **HIGH**   | 8 GB+       | 16384 | K/V q8_0 (or f16) | 8         | 24k chars        | 0.85        | late (80/90) |

### First-run auto-detect
- Look for discrete GPU + VRAM: `nvidia-smi --query-gpu=memory.total --format=csv,noheader,nounits` (or `rocm-smi`).
- Detectable VRAM → pick profile by table. No GPU detected → `LOW`.
- User can override in Settings; profile is stored in config (`hardware_profile`).
- Optional "Benchmark" wizard runs a 5-request probe and prints tok/s + prompt-eval/s + reuse %, then suggests a profile (never silently switches).

## 15. Security & hygiene

- Respect `.gitignore` (via `git ls-files` when repo; fallback exclusion list). Never index: `.git`, `node_modules`, `target`, `__pycache__`, `.venv`, `.xencode` (self).
- **Secrets:** files matching `.env*`, `*.key`, `*.pem`, `*.p12`, `config/credentials*`, `secrets*` are *listed but not read* (presence only). Never paste their contents into summaries or anchor.
- **Binaries:** skip via extension allow-list of source extensions + NUL-byte sniff as fallback.
- File read errors never abort `/init`; they become a warning entry in the summary file.

## 16. Metrics & context meter

Every request produces `RequestMetrics`:

```rust
struct RequestMetrics {
    model: String,
    context_limit: u32,
    prompt_tokens: u32,          // total prompt tokens (llama.cpp)
    cached_tokens: u32,          // prompt_tokens - evaluated
    completion_tokens: u32,
    context_usage: f32,          // 0.0..1.0
    generation_tok_s: f32,
    prompt_tok_s: f32,
    retrieved_files: u8,
    compaction: CompactAction,   // None | Soft | Hard
}
```

- Appended to `.xencode/cache/metrics.jsonl`.
- TUI meter (Provider Health panel / header chip):
```text
Context ██████████░░░░ 72%  · 5,760/8,192 · cached 4,912 · new 848 · ↻ compact
```

## 17. `/init` UX & concurrency

- `/init` is an **async agent job** (spawned task), never blocks chat. Progress via `[INIT]` channel messages (mirrors existing `[BYTEBOT]` plumbing).
- Completion banner:
```text
Initializing project
✓ Scanned 1,284 files
✓ Detected Rust
✓ Built symbol index
✓ Built dependency graph
✓ Summarized 312 source files
✓ Generated project anchor
✓ Generated agent context

Anchor: 1,487 tokens · Index: 2.8 MB
```
- **Resumable/idempotent**: every step checks `manifest.json`/`summaries/`; re-running `/init` skips what's already fresh. Kill-safe (each summary file written atomically: write temp → rename).
- `/init abort` cancels the task (abort handle); partially written files keep resume valid.
- Re-entry guard: `init_running` flag (bytebot pattern).

## 18. Implementation milestones (Rust, atomic commits)

New crate: **`xencode-context-rs`** (scanner, indexer, retriever, budgeter); TUI wires it into `submit_message` via existing `ProviderManager`.

- **M0** Scanner + git snapshot + `files.json`/`manifest.json` + `.xencode/` scaffold + `/init` structural pass with `[INIT]` progress. No LLM. *(deterministic, testable)*
- **M1** Deterministic symbol/dependency extractor (Rust regex first) → `symbols.json`/`deps.json` + tests.
- **M2** LLM file summaries + map→reduce for large files → `summaries/`; anchor synthesis pass; stable ANSI-diff update of existing anchor.
- **M3** Context builder + token budgeter + retrieval scoring wired into `submit_message`; metrics meter in the TUI; expose `prompt_tokens`/`cached_tokens` (providers-rs).
- **M4** Soft/hard compaction + `state.md` + tool-output compression (capture→hash→reference).
- **M5** Hardware profiles + `llama_cpp_args` defaults + first-run detect + benchmark wizard + reuse tuning.

Each milestone compiles, tests green, committed independently.
